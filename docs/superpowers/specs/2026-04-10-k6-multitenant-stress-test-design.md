# k6 Multi-Tenant Stress Test

**Date:** 2026-04-10
**Location:** `docker-demo/stress-test/`

## Goal

Validate that a single Synapse process serving 4 tenants maintains correctness (no cross-tenant data leaks) and acceptable performance (latency, error rate) under concurrent load from 40 users (10 per tenant).

## Components

### 1. `setup.py` — Bootstrap Script

Python script that prepares the test environment against an already-running docker-compose stack.

**Responsibilities:**
- Wait for Synapse to be healthy on all 4 tenants (poll `/_matrix/client/versions` with correct `Host` header)
- Register 10 users per tenant (`user0`–`user9`) via the shared-secret admin API
  - Tenants a/b: use their per-tenant `registration_shared_secret`
  - Tenants c/d: use the global `registration_shared_secret` (`demo_shared_secret_change_in_production`)
- Create one room per tenant via `user0`, invite and join all other users
- Write `test-data.json` containing: per-tenant user credentials (username, password, access_token) and room IDs

**Output format (`test-data.json`):**
```json
{
  "tenants": {
    "matrix.tenant-a.com": {
      "shared_secret": "tenant_a_shared_secret_demo",
      "room_id": "!abc:matrix.tenant-a.com",
      "users": [
        {"username": "user0", "password": "stresstest", "access_token": "syt_..."},
        ...
      ]
    },
    ...
  }
}
```

### 2. `stress-test.js` — k6 Test Script

**VU assignment:** Each VU is deterministically assigned to a tenant and user:
- `tenant_index = vu_id % 4` (0=tenant-a, 1=tenant-b, 2=tenant-c, 3=tenant-d)
- `user_index = Math.floor(vu_id / 4) % 10`

**Load profile (ramp-up stress test):**
```
Stage 1:  0 -> 10 VUs   over 30s   (warm-up)
Stage 2: 10 -> 40 VUs   over 1m    (ramp)
Stage 3: 40 VUs         for 2m     (sustained peak)
Stage 4: 40 ->  0 VUs   over 30s   (cool-down)
```

**Per-iteration flow:**
1. Login via `/_matrix/client/v3/login` (cached — only on first iteration per VU)
2. Send a message to the tenant's room via `/_matrix/client/v3/rooms/{roomId}/send/m.room.message/{txnId}`
3. Read the room timeline via `/_matrix/client/v3/rooms/{roomId}/messages`

**Checks (inline, every iteration):**
- Message send returns HTTP 200
- Timeline read returns HTTP 200
- All senders in the timeline belong to the VU's tenant domain (no cross-tenant leak)

**Isolation check (every 10th iteration):**
- Attempt to read a different tenant's room
- Verify 403 or 404 response (proves schema-level isolation)

**Thresholds:**
- `http_req_duration` p95 < 2000ms
- `http_req_failed` rate < 5%
- `checks` rate > 95%

**Custom metrics (tagged by tenant):**
- `message_send_duration` — Trend, time to send a message
- `timeline_read_duration` — Trend, time to read the timeline

### 3. `run.sh` — Orchestrator

Bash script that ties it all together:
1. Check that docker-compose stack is running (verify `synapse-demo-server` is healthy)
2. Run `setup.py` to bootstrap users and rooms
3. Run k6 (prefer local `k6` binary, fall back to `docker run grafana/k6`)
4. Print summary

## Tenant c/d Shared Secrets

Tenants c and d in `homeserver.yaml` lack per-tenant `registration_shared_secret` and `macaroon_secret_key`. The setup script uses the global `registration_shared_secret` for these tenants. This works because:
- `enable_registration: true` is set globally
- The admin registration endpoint falls back to the global secret when no per-tenant secret is configured

## Prerequisites

- Docker-compose stack running (`docker compose up -d` from `docker-demo/`)
- Tenants c/d schemas must be initialized (keygen and init-schemas services currently only handle a/b — the setup script will document this requirement)
- k6 installed locally or available via Docker
- `/etc/hosts` entries for all 4 tenant domains

## File Structure

```
docker-demo/stress-test/
  setup.py          # Bootstrap: register users, create rooms, emit test-data.json
  stress-test.js    # k6 load test script
  run.sh            # Orchestrator

```
