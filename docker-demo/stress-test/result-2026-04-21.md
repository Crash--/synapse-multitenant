## Permanent instrumentation committed

Task 6 landed DEBUG logs + env-gated assertions in the state-persistence path (`state/store.py`, `state/deletion.py`, `database.py::_set_tenant_schema`). These are not scaffolding — they remain as durable guards. CI can enable `SYNAPSE_MT_STRICT_STATE_GROUPS=1` to fail fast on any future regression that reintroduces writes without tenant context.

## Deferred follow-ups

- **F#1 audit tier 2**: 14 more `@cached` / `@cachedList` decorators surfaced by the audit at `docs/multi_tenant/cache_audit.md` but kept out of scope for this PR (federation destinations, server_keys_json, instance_map, stream-token-only keys, zero-arg MAU counts, `get_partial_rooms`). Each is a same-class leak; a follow-up PR should walk through them with the same TDD pattern.
- **Worker-path invalidations**: the replication-row invalidation sites at `synapse/storage/databases/state/store.py:129-130` and `events_worker.py:461` silently no-op on tenant-scoped caches when invoked without an active tenant context. Not live today (no per-tenant workers), but must be tenant-contextualized before a workers deployment mode ships.
- **Cross-tenant cache invalidation reach**: `@tenant_cached`'s `.invalidate` wrapper auto-prepends the current tenant. Global-sweep invalidations (e.g. during a `/reload` cascade) must go through `.cache.invalidate(...)` directly if they need to reach other tenants' entries.

## Principal-engineer assessment

### Executive judgment

The isolation primitives are production-credible. Two runs, 200 VUs, 5 minutes each, 13,048 events written, 100% cross-tenant rejection, zero `public`-schema leaks, zero strict-mode assertions fired — that is a pass. Ship the fix. Do not conflate this with "multi-tenancy proven at scale" — these tests prove the *mechanism* is correct on a canary workload, not that the SaaS aspiration holds in production shape.

### What the data proves

| Dimension | Evidence | Confidence |
|---|---|---|
| Read-path isolation | `whoami`/`sync` 100%, p95 < 8 ms, no cross-tenant leakage | High |
| Write-path isolation | 13,048 events across 4 schemas, `public.events = 0` | High |
| Auth boundary | 100% cross-tenant token rejection (1,944 probes across both runs) | High for the audited 21 methods |
| Instrumentation as a regression guard | `SYNAPSE_MT_STRICT_STATE_GROUPS=1` fired 0 times under load | Durable — committed, CI-ready |
| Per-tenant DB overhead | ~µs (one `SET search_path` per pool borrow); read latencies indistinguishable from single-tenant | High |

### What the data does NOT prove — the gating constraints on the aspiration

**1. Tenant density.** Four tenants is a smoke test. The economic argument is "one process serves many domains." We have no numbers on "many." Relevant bottleneck math:

- `@tenant_cached` cache footprint grows O(N_tenants × cache_size). Four tenants: trivial. 100 tenants × 1k-entry caches = 100k entries per cache. 1k tenants = 1M. Real memory implications at density we haven't tested.
- `cp_max=10` is a shared connection pool across all tenants. Under contention tenant A can starve tenant B. No per-tenant fairness in the DB layer.
- No test has confirmed the claimed "~150 MB per process" savings materialize.

**Before any customer-facing claim**, run a density test — 50 tenants × 10 VUs each instead of 4 × 200. Different profile, different failure modes.

**2. Duration.** Five minutes catches contention bugs; it misses slow leaks, cache TTL decay, connection pool degradation, metric cardinality blow-ups. A 4-hour run at modest load would surface a different class of issue.

**3. Tenant asymmetry.** All four tenants are identical in these runs. Real SaaS has one customer doing 80% of traffic. Shared pool + shared caches exhibit noisy-neighbor effects under asymmetry — none tested.

**4. Federation.** Not exercised. Phases 9–10 of the roadmap are stubbed and unvalidated at load.

**5. Operations.** `CLAUDE.md` is explicit: tenants cannot be hot-added. For a multi-tenant SaaS that is an operational dealbreaker — every new customer = stop-the-world. Backup/restore is DB-wide, not per-tenant — a misbehaving customer cannot be surgically restored. Not bugs to fix in this PR, but they are the real gating constraints on the aspiration.

### Lessons learned from this PR

The three findings share a pattern worth naming: **multi-tenancy safety requires consistency across three layers** — SQL session state (`search_path`), Python contextvars (`tenant_context`), and Twisted's context/thread boundaries — and every place those layers touch is a potential leak site. Any future contributor touching storage or threading without understanding all three will reintroduce a leak. The Task 6 instrumentation is the only durable defense; keep `SYNAPSE_MT_STRICT_STATE_GROUPS=1` on in CI.

The F#1 audit found 35 leaky decorators; this PR closed 21. The remaining 14 (federation, stream-token caches, zero-arg MAU counters, remote server-keys) are the same vulnerability class, lower severity probably. Do **not** describe F#1 as "closed" in external communication. It is "auth + event/relations tier closed."

### Priority order for what to measure next

1. **Density test** — 50 tenants × 4 VUs each, same total load, different pressure distribution. Does per-tenant fairness hold?
2. **Long-haul test** — 4 hours at 50 VUs. Memory growth, connection pool stats, cache eviction rate.
3. **Finish F#1 tier 2** — 14 more mechanical swaps. ~2 days focused work. Without it, a subtle federation-path leak could nullify the boundary.
4. **Generalized thread-pool contextvar assertion** — today we only guard state-groups. Any unqualified `simple_insert_txn` on a tenant-scoped table is a latent leak. A generalized assertion layer would catch the class, not just instances.
5. **Hot-add + per-tenant workers** (roadmap phase 6) — the SaaS story depends on these. Current answer is "restart the world."

### Final assessment

Ship the fix. It closes a security-boundary bug (F#1), an availability bug (F#2), and makes the product actually usable on fresh installs (F#3). The mechanism is demonstrably correct and has a regression guard. The scale story — tenant density, long-haul stability, operations — is still a research problem, not a product one.
